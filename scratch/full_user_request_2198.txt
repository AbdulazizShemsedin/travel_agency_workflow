CHANGED (2026-09-16): passport OCR now runs on PaddleOCR, not Tesseract
No API shape change -- parse_passport_file/enqueue_parse_passport_file take the same params
and return the same field shape as before. Purely a backend engine swap, but worth knowing why:
after several rounds of Tesseract-specific misread bugs (each fixed individually, each a new
failure mode on a new real passport), switched the primary OCR engine to PaddleOCR -- a modern
deep-learning OCR that does real text detection (finds where the text actually is) instead of
needing a guessed crop, and includes its own orientation correction. Verified against both real
passports on file: it read the full, untouched image correctly in a single pass on both,
byte-exact against the true MRZ, including the low-resolution one that needed several rounds of
Tesseract-specific fixes to get right. The whole previous Tesseract/PassportEye pipeline is kept
intact as an automatic fallback if PaddleOCR isn't available or doesn't produce a usable read --
this is an addition ahead of it, not a replacement, so it can't regress anything that worked
before.
Heads up on deploy: this adds ~1GB to the backend Docker image (PaddleOCR's deep-learning
dependencies) and the OCR call itself takes several seconds per image (2-20s observed) rather
than Tesseract's near-instant read -- expect a noticeably longer build/deploy.
Action needed: parsePassportFileV2 (documents.ts) calls the synchronous
parse_passport_file directly, not the async enqueue_parse_passport_file + poll pattern that
already exists in the backend for exactly this "OCR can be slow" scenario. A 2-20 second
synchronous call on the passport upload step is going to feel like a hang/freeze in the UI now --
switch this call to the async endpoint (poll background_jobs.get_job_status(job) for the
result) before this ships to a real user.
FIXED (2026-09-16): passport OCR — stop pre-cropping to the MRZ before upload
Action needed: if your passport upload flow crops the image down to just the MRZ strip
before sending it (a workaround for OCR failing/returning garbage on the full photo), stop
doing that — upload the full passport photo like any other document. Two problems, one fix:
The garbage-name bug (cjjjjjsjadnajdnajdnajsdnj-type results) is fixed. Root cause: on a
full, uncropped photo, the OCR could lock onto the wrong region of the image (the photo
border, a security pattern, other printed text), and since passport names carry no checksum
at all in the MRZ standard (unlike the passport number/DOB/expiry, which do), garbage from the
wrong region had nothing checking it before landing in first/last name. Fixed by requiring the
document number, DOB, and expiry checksums to all agree before a name is trusted at all — if
they don't, the result now comes back with those fields blank and needs_passport_review: 1
instead of a confident-looking wrong name.
This is also why cropping was breaking the CV: whatever image you upload for OCR is the
same one that ends up as the stored passport photo — crop it down to the MRZ strip and that's
what shows up on the generated CV instead of an actual passport photo. OCR no longer needs the
pre-crop (see below), so uploading the full photo fixes both problems in one move.
Why the full photo works reliably now: the backend no longer solely depends on the MRZ
auto-detector finding the right region. It also corrects photo orientation (sideways/upside-down
phone photos) and tries several MRZ-band crops itself (the MRZ is always at a fixed position at
the bottom of a passport's bio page), independent of whether the auto-detector succeeds. Verified
against synthetic passport photos with decoy text/patterns elsewhere on the page, rotated 90°/180°,
and tilted up to 15° — all read correctly; a photo with no real MRZ at all correctly returns
nothing rather than a guess.
No API shape change — parse_passport_file/enqueue_parse_passport_file take the same
file_url param and return the same field shape as before.
UPDATE (same day): a live test surfaced a second, narrower bug in the same area: two given
names could get glued into one ("ASNEKECHSTEDESSE" instead of first="Asnekech"/middle="Tedesse")
when the OCR misread the single separator character between them as a stray letter. Fixed by
having the pipeline keep trying its other crop attempts (it already tries several, at different
effective resolutions) whenever a name looks suspiciously long, instead of stopping at the first
attempt that got the passport number/DOB/expiry right — a different crop can OCR the exact same
line's separator more cleanly. If every attempt still comes back with a suspiciously long name,
it's now returned with needs_passport_review: 1 instead of looking like a clean, confirmed
read — worth surfacing that flag in the UI if you don't already (e.g. a small "please verify"
badge) so staff know to double-check.

No API shape change, purely a backend correctness fix that changes who shows up as
allocated_to on one of the ToDo rows list_my_todos returns. When a Placement reaches
Stamped, the officer who handled its LMIS step gets a personal "Book ticket for..." ToDo
alongside the broadcast to every Ticketer (continuity, so the LMIS person can follow their case

1. Invoice PDF: TOTAL line now diverges from balance_due_original — important
The printed Commission Batch invoice's bottom-line TOTAL is now:
Batch Total + Advance (requested_advance_amount) + Unpaid from previous batches (previous_unpaid_original)
